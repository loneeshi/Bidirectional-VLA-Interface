# S1 原生 Pick 0/10：失败归因与修复

记录时间：2026-09-17，美国东部时间（EDT）。主线停在 **S1 原生能力门**；SFT 已完成，TAPT/S2 尚未放行。本次没有重训或更换检查点。

## 结论及证据强度

已定位的行为问题是 **接近、对齐和闭爪时机不足**，发生在稳定抓取之前。十个起点均未检测到持物，因此不能归因为“抓到后没有回到 rest pose”。固定教师观测下也存在首动作及夹爪方向错误，包含已用于训练的父轨迹；这使“只是在线新起点问题”不足以解释失败。

尚未确定唯一训练根因。当前证据不能把问题全部归于视觉、单次 epoch、LoRA 容量或动作接口，也不能证明新增校验后策略就会成功。实际能力成绩仍为 **0/10**。

距离是诊断量，不是新增成功阈值。所有回合均未持物，八个回合甚至没有进入 20 cm 范围。九个完整回合中，夹指曾从接近 5 cm 开度闭合到接近零并再次打开，因此“闭爪指令根本没有发出”不成立。

较接近的 seed2028 在第 134 动作后仍有约 19.1 cm 偏差，其中横向约 15.6 cm；随后闭爪时并未对齐。seed2030 的最近点出现在第 15 动作后，仍约 16.9 cm，之后离开目标。完整回合底盘累计行走约 2.24–3.51 m，存在无效移动。

1816 个实际动作中，1280 个动作至少一维超出控制器范围后被裁剪（70.5%）；2306 / 23608 个标量被裁剪（9.77%）。这说明输出饱和频繁，**还不能说明裁剪本身是错误**：不得取消控制器的合法范围限制。head 两维原始输出最大绝对值仅约 1.26e-7，head mask 不是这次的大误差来源。

九个回合只有 199 动作，来自原生 reset/evaluate 的 horizon 计数；不是本次摘要脚本少记一步，也没有因此修改预算或原生判据。

## 2. 教师观测上的实际动作检查

Fetch 该控制模式下正值趋向开爪、负值趋向闭爪。在 train 父轨迹 0/17 上，模型与专家方向相反；validation 20/20 也出现相反方向。在线每次只执行动作块的第一个动作，整块平均误差较小并不保证实际执行的首动作正确。

这是小样本诊断，不能估计全数据动作准确率或唯一因果机制。使用单次固定随机数，不以这些样本选检查点、调阈值或主张模型全面失去动作能力。有效证据：[run02 summary](results/s1-failure-attribution-2026-09-17-run01/s1-teacher-action-audit-2026-09-17-run02/summary.json)。

## 3. 已检查的接口与仍未排除的因素

## 4. 为什么 0.1241 的 loss 不能代表抓取能力

作者 action loss 是 **flow 速度目标误差**，内部动作补齐到 32 维后求平均；Fetch 实际只有 13 维。它不是本报告的控制器动作 MSE，也不是成功率。

LeRobot 在轨迹末端重复最后一个动作来补齐动作块，当前 S1 repack 没有传递它的 `actions_is_pad`。固定 150 帧验证集取每条父轨迹首/中/末帧；末帧各有 9 个重复目标，即总 1500 个目标时点中 450 个来自末端重复。验证使用固定噪声/时间采样，训练则按更新步正确变化随机数，没有发现训练随机数每步重复的 bug。

这些限制会影响 loss 的解释，但本轮沿用作者动作学习目标，**没有事后换 loss、改检查点选择规则或重新包装原成绩**。后续训练须并列报告首动作、有效时段的真实 13 维误差与在线能力，不再将一个 padded loss 值当作通过依据；若更改 padding loss mask，应单独登记方法差异。

## 5. 本次具体修复

1. `fetch_native_s1_config.py` 强制绑定 **训练数据 manifest → 归一化来源**，并拒绝不明确或开启 delta 转换的配置。本轮来源本来匹配，这是预防后续误接，不是 0/10 的已证根因。
2. `eval_native_s1.py` 增加原生失败原因，分别记录耗尽 horizon、累计力超限等，不再只输出笼统的 fail；不改变动作与判据。
3. 教师动作审计按真实导出区间采样并截断有效预测时段，保留首动作/动作块误差；增加 H5 → manifest → normalizer 哈希关联校验。
4. 离线汇总要求固定十个不重复 seed、完整 episode 状态和逐动作事件连续性；基础设施中断不能被混成一次正常策略失败。

上述是接口保护、证据质量和可解释性修复，尚没有一次新的在线成功验证。原生 0/10 不变，S2/S3 仍未放行。

验证：60 项相关 CPU 测试通过；真实 train/validation loader 均通过新来源校验并读取预处理样本。18:26 EDT 对原始 H5、medium manifest 和实际 normalizer 补做 CPU 哈希复核通过，见 [来源与资源核验](results/s1-failure-attribution-2026-09-17-run01/provenance-and-resource-check.json)。这份复核发生在 run02 之后，保留为独立证据，不改写原始 run02 日志。

## 6. 下一步与止损

1. 在新训练前先做一个有界的 **同起点专家动作回放**，核查 H5 状态恢复、wrapper/controller 与渲染差异；保留全状态及控制器状态，不能把几项数组相等称为完全同起点。若发现执行接口问题，先修并用同一冻结检查点复核，另存结果。
2. 接着执行计划允许的一次 **独立特权 state 诊断臂**：同父轨迹划分、同动作与更新预算，冻结输入字段和专用 train-only 归一化。启动前核算 S1 累计 18 小时上限、登记时长，不新增租机/API。不能把它算作忠实 RGB 臂或用其成功直接放行 S2。
3. 该对照若改善，只能支持“目标/状态可观测性相关瓶颈”；若不改善，仍需区分优化、容量、动作和数据问题，不能自动断言一定是接口 bug。一次对照无法穷尽因果。
4. 原生门仍为固定 10 起点至少 3 成功。S2 另需 native24 错误交接验证，继续保留当前冻结；C 线按独立对照口径推进，不冒称 TAPT。
