## 0. 为什么是流水线而不是并行

TAPT 是后训练：论文把 π₀.₅ 从 92.4 修到 97.2，GRPO 要求采样里存在奖励差异。**在一个原生成功率为 0 的骨干上训工具族残差和进度头，产生的是日志而不是结果**——9/16–9/17 在 AC-DiT 上的 1199＋118 次更新、两轮进度校准、0/5 与 0/2 就是这个结论的实证。所以本周按依赖顺序推进，每一级有明确入场门：

```
S1  π₀.₅ 在 Fetch 上完成原生 Pick        ← 论文的目标域 IA SFT，TAPT 的前提
      ↓ 门：10 起点 ≥3 成功
S2  调用切分 + 四族残差 + 进度头联合训练  ← TAPT 本体
      ↓ 门：选定检查点，留出进度 MSE 与误完成率可接受
S3  GPT + LightNav-0 + TAPT π₀.₅ 在线链   ← 完整方法闭环
S4  DROID 中间阶段、GRPO                  ← 明确列为本周差异，见 §5
```

与流水线并行的是 **C 线：对照条件**（§4）。它不是 π₀.₅ 的替代品，是论文 Table 1 本来就需要的基线行；没有它，S3 即使跑出来也没有可比对象。

## 1. S1：π₀.₅ 的 Fetch 目标域 SFT

### 数据
官方 `set_table` 苹果 Pick 示范（9/16 已下载校验，Pick/Place 各 1000 条，19.3 GB）。**忠实臂**输入用原生 head/hand 128×128 RGB ＋ qpos/qvel（不给物体位姿），动作 13 维官方 wrapper 后——这才是论文的 π₀.₅ 观测形态，也是可以叫"复现"的那一版。按完整轨迹 20/5 划分，不混入评估起点。

### 为什么这次和前七个变体不同
V8 用的是 1228 帧 / 30 段 / 单场景单初始化；这次是 300 条完整示范、多起点。前七次失败的主要假说是数据规模和起点多样性，这一次直接检验它。

### 吞吐门
先转 20 条、训 100 步测吞吐。≥1 样本/秒 → 300 条示范、留 50 条验证、目标 ≥2 epoch；0.5–1 → 150 条、1 epoch；<0.5 → 用 Runpod 余量租 A6000 ≤6 小时做同一件事，再不行报告"单卡吞吐不足以在本周完成目标域 SFT"并停。训练墙钟上限 18 小时。

### 出场门
`set_table/pick/013_apple` val seed 2024–2028 ＋ 2030–2034 共 10 起点原生评估，与 AC-DiT 0/5、V8 0/5、SAC 正参照同协议，直接可比。**≥3/10 进入 S2。**

### 不通过时的诊断臂
同数据同训练，改用官方特权 state（含物体/目标位姿、grasp 标志，与 MS-HAB 官方 BC/DP 基线同口径）再训一次。能抓 → 瓶颈在从图像找目标，结论是"这条复现需要的数据量/视觉预训练超出本周资源"；仍不能抓 → 瓶颈在动作语义或归一化适配，结论是接口层还有 bug 要查。两种结论都是要发给胡学姐的实质信息，不是空手。

## 2. S2：TAPT 本体（入场门通过才启动）

四个工具族 reach / grasp / move / release，共享冻结的 π₀.₅ 骨干，每族一组 LoRA 残差，一个共享进度头，动作损失 ＋ 0.1 × 进度 MSE。族由高层标签确定性路由，不是学习式门控。

- **调用切分**：复用 `fetch_segments.py` 的接触/夹爪/持物证据分段，按完整轨迹划分后再切调用窗口；失败结尾不标完成。
- **进度标签**：当前帧语义（`current_observation_v2`，与作者 `data_loader.py` offset=0 一致），在线在执行动作前消费 index 0。9/17 已经确认过这个契约，直接沿用，不重新讨论时点。
- **训练**：20 更新梯度/显存门 → 有界 SFT，按固定留出联合损失选检查点，测试成功率不参与选择。
- **出场门**：留出进度 MSE、调用起点误报率、教师完成端点预测三项都报；进度头不可靠时 S3 仍可跑，但进度只作影子评估，不接管切换——这一点必须在报告里写明。

CPU 侧的切分和数据准备**周四晚就做**，不等 S1 结果，这样 S1 一通过 S2 立刻能启动。

## 3. S3：完整在线链

GPT-5.6 organizer ＋ `mshab-tool-family/1` 接口 ＋ LightNav-0 导航 ＋ TAPT π₀.₅ 操作，在固定起点上跑单物体链，再按时间余量扩到多物体。决策空间：`navigate(z)` / `pick(z)` / `place(z)` / `retry` / `reposition` / `observe` / `abort`；benchmark 子任务顺序保留，不兼容的请求记录并拒绝、不暗中替换。学习进度触发完成、停滞、回退三类事件，阈值沿用已 port 的作者默认值，本周不调。

## 4. C 线：对照条件（与流水线交替占用 GPU）

论文 Table 1 的可比性来自三行对照。本周用 LightNav-0 ＋ 官方 SAC 把这三行先跑出来：

| 条件 | 高层 | 低层 | 反馈 | 对应论文 |
|---|---|---|---|---|
| C1 | 官方 sequential oracle 顺序 | SAC/PPO | 无 | standalone |
| C2 | GPT organizer | SAC/PPO | 调用结束状态＋规则进度代理＋事件打断 | 普通策略＋planner 包装 |
| C3 | GPT organizer | SAC/PPO | 独立学习进度头 | 接口完整（进度头不在 VLA 骨干上） |

C3 的进度头训在 SAC rollout 上——被监控的工具就是 SAC，在线分布与训练分布一致，这是它和 AC-DiT 那个头的本质区别。三条硬约束：

- **不能是无条件标量函数。** 相同 RGB/qpos 在不同调用阶段进度不同，输入必须绑定当前工具族 g 与目标指令 z，编码方式在训练前冻结。
- **划分预注册、不许泄漏。** 训练用 train scene seeds 100–109，开发用 train seeds 120–124，最终评测的 val seeds 0–9 不进入训练、阈值选择或检查点选择。**不能训在 C1 的最终测试轨迹上再拿 C3 和它比。**
- **失败尾不标完成。** 无法从真实证据确定进度的失败帧用 mask，不强行线性拉到 1。

离线报 MSE 与失败轨迹上的误完成率，过不了就 C3 不上线、如实写未完成。PPO 与 LightNav 的交接分布不同，LightNav 面板的 C3 需要独立影子验证，不宣称分布自动一致。

**GPU 排队**：默认所有 GPU 工作串行，包括 PPO/SAC 渲染——CPU 物理仍然要 GPU 渲染，不能只按显存余量推断可以并发。如果要让 C 线和 S1 训练同时跑，必须先实测一次并发下的吞吐和显存峰值再决定；LightNav 推理 18 GB，无论如何排在训练结束之后。

**口径**：SAC 不是 VLA，给 SAC 加进度头不是作者 TAPT。**官方 SAC 不读语言 z**——runtime 只能记录指令并按已校验的目标选择对应策略，不能说自然语言进入了 SAC 网络；只有导航和 VLA 后端才可能真正消费 z。固定子任务顺序、oracle 目标、恢复动作扩展、独立进度头和 SAC 本身，全部是与论文的差异，不能写成"高层无差异"。C 线是对照与保底，任何报告里都不能把它说成 VLM＋VLA tools 复现。
