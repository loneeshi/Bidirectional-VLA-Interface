# 本周可行方案 v2：在 MS-HAB 上做 VLAs-as-Tools baseline（2026-09-17 → 09-21）

写给：Shuai 与自动推进的代理。目标：周日（9/21）拿到一个可以放进 proposal 的 baseline——高层 VLM 通过 (g, z) 调用工具、接收进度/事件反馈、事件触发重规划，在 MS-HAB 的长程任务上跑通并有固定 N 的对照数字。研究对象（双向语义接口）以后要和它比，所以它必须是论文的接口形态，而工具是什么可以先妥协、后替换。

依据：仓库 `0042ffd` 全部 docs/results、9/14 计划、9/14–9/17 每日进度、9/12 proposal、VLAs-as-Tools 精读。资源：实验室 GPU1（Quadro RTX 8000 48 GB，GPU0 他人占用）、Runpod 授权余量约 USD 5、GPT API 每次约 USD 0.0005、一人＋代理、4 个工作日。

## 0. 先把"baseline 做完"定义清楚

论文系统有四个部件。本周能真做的、必须替代的、以及替代后必须在报告里写明的差异如下。

| 论文部件 | 本周实现 | 与论文的差异（写进报告） |
|---|---|---|
| 高层 VLM：分解任务、发 (g, z)、按反馈重规划、恢复 | GPT-5.6 organizer ＋ `mshab-tool-family/1` 接口，已有 | 无差异；子任务顺序沿用 benchmark 顺序（不做自由排序） |
| 工具族 VLA：共享骨干＋按族残差 | 导航 = LightNav-0（VLA 类）；操作 = 官方按物体 SAC Pick/Place（占位） | **操作工具不是 VLA、无 TAPT 残差**；支线 B 若通过，Pick 面板换成 π₀.₅ |
| 进度反馈 ψ_ω ＋ 阈值监控 ＋ 事件触发重规划 | 条件 2 用规则进度代理；条件 3 用在 SAC rollout 上训的独立学习进度头 | 进度头不在 VLA 骨干上；阈值沿用作者 port，不调 |
| 长程任务与评测 | MS-HAB TidyHouse 5 物体，固定 10 个 val episode | N 小；任务级 SR 预期接近 0，主指标改为"完成到第几个物体" |

这版 baseline 能证明的是论文的**接口一半**：事件反馈＋恢复相对固定调度器有没有收益、代价是多少次 VLM 调用。它不能证明**训练一半**（TAPT 对齐 vs 普通 SFT）。这一半留给支线 B 和下周。

## 1. 为什么这是可行性最高的版本

所有需要的基础设施都已经存在并跑通过：GPT organizer 正常链与注入故障恢复、LightNav＋SAC 单物体链 B11、tool-family 接口、进度监控 port、逐调用记账、审计脚本。唯一缺口是 Fetch 上的操作 VLA，而它三天内换了三个骨干都是 0。用官方 SAC 占位以后，主线不再被这个缺口阻塞；π₀.₅ 改成一个有预算、有止损的并行赌注，成功就换入（接口相同，零工程），失败不影响周日交付。

我的估计：主线 A 周日交付概率约 85%（风险是 5 物体链的集成 bug 和时间）；支线 B 在分布内 Pick 达到换入门槛的概率约 30–40%。

## 2. 主线 A：接口完整的 baseline（保交付）

### A1 决策空间

VLM 每次决策从下面选一个，并为需要落地的调用写 z（grounded instruction）：`navigate(z)`、`pick(z)`、`place(z)`、`retry`（同技能重发）、`reposition`（短导航重新站位，上限 40 步）、`observe`（不动，刷新图像）、`abort`。benchmark 子任务顺序保留，由 runtime 校验请求是否与当前子任务兼容，不兼容的请求记录并拒绝、不暗中替换。这比现在"每步只有 1 个允许技能"多了恢复层面的真实选择，又不需要动评分 pointer。

### A2 反馈（低到高）

每次调用返回：`status`（succeeded/failed/timeout/interrupted）、`progress`（条件 2 为规则代理，条件 3 为学习进度）、`evidence`（grasp 标志、TCP–目标距离、累计力、步数）、`reason_code`。调用中每 N 步检查一次进度事件：阈值完成、停滞、回退；触发即打断并把新图像交给 VLM。事件阈值沿用已 port 的作者默认值，本周不调。

### A3 三个对照条件

| 条件 | 高层 | 反馈 | 对应论文里的哪一格 |
|---|---|---|---|
| 1 固定调度器 | 官方 sequential 评测的 oracle 顺序调用 | 无（只有 benchmark 终止） | standalone / 无接口 |
| 2 VLM ＋ 规则反馈 | GPT organizer | 调用结束状态＋规则进度代理＋事件打断 | 接口，但进度非学习 |
| 3 VLM ＋ 学习进度 | GPT organizer | 同上，但进度来自独立进度头 | 完整接口（进度头不在 VLA 上） |

条件 3 的进度头：小网络，输入工作台 RGB＋qpos，输出调用局部进度，训练数据是条件 1 跑出来的 SAC rollout（成功与失败都进，失败尾不标完成）。为什么这次可能靠谱而 AC-DiT 那个不靠谱：被监控的工具就是 SAC，在线状态分布和训练分布一致；之前是工具自己漂出分布，头看到的全是没见过的状态。离线先报 MSE 和失败轨迹上的误完成率，过不了就条件 3 不上线、如实写"未完成"。

### A4 评测协议（预注册，开跑前冻结）

任务 TidyHouse，val 场景，10 个固定 episode（seed 与 plan uid 写进 config）；每 episode 上限 7000 步、VLM 调用上限 40、API 上限 USD 0.05；导航主面板 LightNav-0，另跑 PPO 导航作为控制。指标：完成物体数（0–5，主指标）、逐子任务 SR、任务 SR、总步数、VLM 调用数与费用、无效请求数、恢复尝试数及成功数、墙钟。全部 episode 保留，基础设施失败单列不删分母。

### A5 算力与时间

SAC/PPO 很小，CPU 物理；LightNav 推理约 18 GB、1.4 s/次。估算每 episode 10–20 分钟，10 episode × 3 条件 × 2 导航 ≈ 10–20 小时 GPU1。**LightNav 面板不能和支线 B 训练同时占 GPU1**（π₀.₅ LoRA 训练约 30 GB 以上），PPO 导航面板可以。日程按此错开。

## 3. 支线 B：π₀.₅ 作为 Pick 工具（有界赌注）

目的：给胡学姐说的 "pi05 for manipulation" 一个本周内能回答的实验，并顺便回答"Fetch 上 π₀.₅ 失败是感知还是控制"。

### B1 数据

官方 `set_table` 苹果 Pick 示范 1000 条（9/16 已下载校验 19.3 GB，含 Place 1000 条）。输入用原生 head/hand 128×128 RGB（放大到 224）＋**官方 state（含 TCP 位姿、物体位姿、目标、grasp 标志）**，动作 13 维官方 wrapper 后。用官方 state 是刻意的：它把感知问题拿掉，只测"π₀.₅ 能不能在 Fetch 上学会控制"；MS-HAB 自己的 BC/DP 基线也是这个 state，报告里写明"state-conditioned"。只做 Pick 一个族，不做工具族残差，不做进度头。

### B2 预算与吞吐门

先转 20 条示范、训 100 步测吞吐。≥1 样本/秒：用 300 条示范、留 50 条验证、目标 ≥2 个 epoch；0.5–1 样本/秒：150 条、1 epoch；<0.5：放弃 GPU1 训练，用 Runpod 余量租 A6000 ≤6 小时做同样的事，再不行就停。总训练墙钟上限 18 小时，落在周五晚到周六中午。

### B3 换入门

在 `set_table/pick/013_apple` val seed 2024–2028 ＋ 2030–2034 共 10 个起点上原生评估（与 AC-DiT 0/5、V8 0/5、SAC 正参照同协议，直接可比）。Pick ≥ 3/10：换入主线 A，在 set_table Pick 面板（10 起点）上跑条件 1/2/3，作为报告里的"VLA 工具面板"。< 3/10：不换入、不二次训练，把数字和录像写进报告。

### B4 止损

本周只训一次；不调阈值、不换相机、不加恢复数据、不做 TAPT 残差。任何"再训 2000 步试试"都推到下周并先给理由。

## 4. 本周明确不做的事

Fetch 上的 TAPT 残差训练、进度头校准和错误交接进度验收（AC-DiT 线全部冻结）；AC-DiT；作者 π₀.₅ 的 BF16/FP32 数值门续做；DROID 中间阶段；GRPO；LIBERO 任何新实验；自由子任务排序；"search"（无 oracle 目标）设定。这些都是下周或更晚的题，本周碰它们就是在重复过去三天。

## 7. 风险与降级

5 物体链没跑过：条件 1 周五上午就先跑，集成 bug 在周五修完。LightNav 打转拖时间：主面板改 PPO 导航，LightNav 缩到 5 episode。GPU1 被占：支线 B 转 Runpod 6 小时或直接放弃，主线 A 用 PPO 导航全跑（不需要大显存）。API 桥接不稳：沿用已有 durable claim 与重试，基础设施失败单列。进度头离线不达标：条件 3 不上线。支线 B 0/10：如实报告，把它当成对"感知还是控制"的一个回答（用了官方 state 仍 0 → 问题在动作/控制适配，不在感知）。
