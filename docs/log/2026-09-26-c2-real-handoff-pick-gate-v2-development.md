# C2 第三步：Pick 前站位门控开发批（V1、V2，2026-09-26 UTC）

## 一句话结论

**GPT 还没有学会"什么时候该挪一下底盘"。** 两版提示词下，GPT 几乎对每个交接都建议前移（V1：60/60，V2：57/60），因此预先设定的"有选择性"门槛没有通过，新交接上的验收**没有运行**。

## 背景：第三步要回答什么

- [第二步救回扫描](2026-09-26-c2-real-handoff-pick-rescue-main.md)发现，在 SAC Pick 开始前先把底盘前移 10 cm（`forward_10`），能救回一部分原本失败的 Pick。
- 但这个动作也可能把原本会成功的 Pick 弄坏。所以真正的问题不是"要不要前移"，而是**哪些交接该前移、哪些不该**。
- 第三步让 GPT 在 Pick 开始前看一眼交接现场（头部和手部相机各一张图，加上第 0 步的几何量），判断要不要前移，再和不用 GPT 的方法比较。
- 两批都只用第一步普查中已有的 60 个真实交接（开发集）。原计划是先在开发集上确认 GPT 的判断"有选择性"，再到约 120 个新交接上正式验收。

**各组含义**（后文都用这些名字）：

| 组 | 做法 |
|---|---|
| 原基线 | 普查中第一次跑出的结果，不做任何动作 |
| 无动作复跑 | 从同一快照再跑一次、不做动作，用来衡量随机波动 |
| 总是前移 | 每个交接都先前移 10 cm |
| 几何规则 | 用开发集定下的几何阈值决定是否前移 |
| GPT 门控 | 由 GPT 的判断决定是否前移 |
| 事后阈值 | 在同一开发集上挑出最好看的 GPT 概率阈值，只作参考，结果偏乐观 |

### 观察与结论

- **观察**：GPT 对每个交接都说"要干预"，等于总是前移，根本没有回答"什么时候该干预"。它给出的失败概率也系统性偏高。
- **结论**：V1 不进入验收，也没有执行前移动作。改做 V2：不再问"要不要干预"，而是分别预测"前移"和"不动"各自的成功概率，只在前移更好时才动。

## 实验 #002：V2，GPT 预测"前移比不动好多少"

- **日期**：2026-09-26 UTC
- **要回答的问题**：
  1. 在全部 60 个交接上，"总是前移"是否同时带来救回和误伤？
  2. 让 GPT 预测前移带来的成功概率提升，只在提升为正时才前移，这个判断是否有足够的选择性，值得拿到新交接上验收？
- **run 名称 / ID**：`real-handoff-pick-gate-v2-development`；输入清单 SHA256 `617a6390764cdf662f7c398ff5cd8e509a6c5cbefe11364f9ff6fbe138a2da17`；快照绑定 SHA256 `142503ddbcb1fe60b566e42aa6402fbc84db169d40b68485c2613e5e65cc9e5a`
- **代码版本**：条件运行器 SHA256 `0a1576d075a9eb9f8e3612f69439827aa6d0157a5bff07679c9435c9ccaedaf7`；其余哈希见 [V2 诊断](../../research/c2/diagnostics/2026-09-26-real-handoff-pick-gate-v2-development.md)。工作区快照，未对应已发布 commit
- **环境**：MS-HAB TidyHouse sequential validation；实验室 GPU1 Quadro RTX 8000。Python、ManiSkill、PyTorch 版本未在本公开摘要核实

### 配置（评测参数）

| 项 | 值 |
|---|---|
| 任务 & 数据划分 | 普查的 60 个真实交接（开发集）；新交接验收不在本批 |
| plan roster / episode 数 | 每个交接真实跑两条：无动作复跑、总是前移，共 120 条。原基线沿用普查第一次的结果。几何规则、GPT 门控、事后阈值三组不另跑：决定前移就取"总是前移"那条的结局，决定不动就取原基线 |
| 导航策略 | 不重跑，使用普查的交接快照 |
| Pick / Place 策略 | 官方逐物体 SAC；只测 Pick |
| 调度器 / 通讯协议 | GPT（`gpt-5.6-luna`）对每个交接给出两个概率：前移后成功、不动成功。两者之差为 `d`，`d > 0` 就前移 |
| observation / policy state | 同 V1：两张 128×128 图像加第 0 步几何量，不给任何结局 |
| skill horizon / episode 上限 | Pick 200 步和累计力上限不变；前移最多占 80 步，计入同一 Pick。路线检查拒绝前移时按不动计；前移没到位时从实际位置继续 SAC，按实际结局计分 |
| 模型调用与费用边界 | ≤ 60 次请求、每次输出 ≤ 1,024 token、预留上限 USD 2.50；GPU1 ≤ 6,000 进程秒，单进程 ≤ 300 秒 |
| 其它关键设置 | **进入验收的前提**（事先写定，须全部满足）：120 条和 60 次请求齐全；原基线与无动作复跑结局不一致 ≤ 12；总是前移的救回和误伤各 ≥ 4；GPT 门控前移 10–50 次；GPT 门控与几何规则至少 10 次决定不同 |

### 结果

**各组在 60 个交接上的严格 Pick 成功数**（救回、误伤均相对原基线而言）：

| 组 | 前移次数 | 成功 / 60 | 救回 | 误伤 | 净变化 |
|---|---:|---:|---:|---:|---:|
| 原基线 | 0 | 40 | — | — | — |
| 无动作复跑 | 0 | 43 | — | — | +3（没有任何动作，纯随机波动；与原基线不一致 5 次） |
| 总是前移 | 60 | 40 | 7 | 7 | 0 |
| 几何规则 | 34 | 43 | 5 | 2 | +3 |
| **GPT 门控** | **57** | **39** | **6** | **7** | **−1** |
| 事后阈值（`d > 0.065`，仅参考） | 25 | 41 | 4 | 3 | +1 |

**进入验收的前提条件**：

| 条件 | 实测 | 是否通过 |
|---|---:|---|
| 120 条条件与 60 次请求齐全 | 全部齐全 | 是 |
| 原基线与无动作复跑不一致 ≤ 12 | 5 | 是 |
| 总是前移：救回 ≥ 4 且误伤 ≥ 4 | 救回 7、误伤 7 | 是 |
| **GPT 门控前移次数在 10–50 之间** | **57** | **否** |
| GPT 门控与几何规则决定不同 ≥ 10 | 23 | 是 |

| 其它指标 | 值 |
|---|---|
| 执行情况 | 120/120 条完成，失败或超时 0。其中 3 条前移被路线检查拒绝（按不动计），12 条前移没到位后继续 SAC |
| GPT 预测的提升 `d` | 60 个中 57 个为正，中位数 0.06，范围 −0.06 至 0.13 |
| 仿真与时延 | 8,081 个仿真动作（底盘 1,764、SAC 6,317）；GPU1 4,179.03/6,000 进程秒，最长单进程 47.2 秒 |
| API 请求 / 费用状态 | 60/60 有效，零重试；33,259 输入 / 12,980 输出 token，估算 USD 0.0222，实际账单未取得。实验室不向项目收费（用户确认） |

### 观察与结论

- **前移本身有利有弊，两边正好抵消。** 总是前移救回 7 个、误伤 7 个，净变化为 0。这说明"何时前移"确实是个真问题。
- **GPT 仍然几乎总说前移。** 57/60 个交接的预测提升为正，而且数值都很小（中位数 0.06）。GPT 门控基本等于总是前移，净变化 −1。
- **±3 以内的差别分不清是方法效果还是运气。** 无动作复跑什么都没做，成功数就比原基线多 3 个。几何规则的 +3、事后阈值的 +1 都在这个范围内。而且它们都是在同一开发集上定的规则，不是独立验收成绩。
- **结论：V2 不进入验收。** 唯一没通过的前提是 GPT 门控的选择性（57 次，要求 10–50 次）。按事先约定，不在同一开发集上改提示词或换阈值来凑过门槛。
- **本批不能说明的事**：前移动作或 GPT 判断在新交接上有没有净收益，本批没有回答；也不能据此断言 GPT 在所有提示方式下都无法判断。
