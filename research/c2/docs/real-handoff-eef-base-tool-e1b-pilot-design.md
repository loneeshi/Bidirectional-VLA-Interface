# 底盘工具纳入与 E1-B 特权试点（设计草案）

**状态（2026-09-29 UTC）：v12底盘冒烟第20号通过，随后监督器记录错误导致停止；剩余四例续跑待批，E1-B未授权。** 本设计已用47.275746 GPU1进程秒、27环境步，API0。见[CPU诊断](../diagnostics/2026-09-29-eef-base-tool-cpu/README.md)及[待批冒烟提案](real-handoff-eef-base-smoke-authorization-proposal.md)。

**用户 2026-09-29 决定：**把底盘纳入 Astra 的工具集。

- 主设计：[末端工具闭环设计](real-handoff-eef-tool-loop-icl-design.md)。
- 前序：[工具冒烟与 E1 试点设计](real-handoff-eef-tool-smoke-e1-pilot-design.md)，结果见 [E1 r2 诊断](../diagnostics/2026-09-29-eef-e1-pilot-r2/README.md)。

## 为什么要纳入底盘

1. **固定底盘的前提不成立**。原设计让底盘固定在交接站位，依据是"SAC 在这些交接上成功过，说明可行"。但 SAC 在 Pick 过程中自己也在移动底盘：第 5／8／11 号教师的底盘最大平移分别为 0.324／0.496／1.059 m。在 MS-HAB 里，Pick 本身就是移动操作任务。
2. **E1 r2 第 11 号的提议末端位姿超出固定底盘的末端原点可达上界**。目标包围盒中心距底盘约 1.99 m，而由 URDF 算出的末端原点水平可达半径上界约 1.14 m。Astra 用 `check_path` 确认无解后放弃。这揭示了条件设置的可行性论据不足，不能据此归因于 Astra；该末端原点上界不构成所有物体接触抓取方式的穷尽证明。
3. **对应组会的原始设想**："Pick 失败后，GPT 调整位置再重试"。

E1 r2 的 1/3 保持原分母，不事后修改。第 5 号成功是固定底盘条件下的存在性证据。

## 先修 E1 暴露的两个问题

1. **部分移动后，段终点没有更新**：某次移动只走了一部分，执行器仍把旧起点记作 `last_plan_endpoint`。之后的路径，连"保持当前实测姿态"的零位移路径，都被判为跳解（第 8 号连续被拒 8 次）。
   - 修正：每条运动指令结束后，无论是否到位，都以实测关节状态作为下一条指令的跳解比较起点。
   - 证据见 `boundary-bookkeeping-cpu.json`。
2. **工具参数说明不清**：非 `set_gripper` 指令的夹爪字段必须填 null，这个跨字段约束在工具说明中没写明白，两例各出现 1 次无效参数。
   - 修正：在工具说明里写明，并在参数无效时返回可读的错误。

## 底盘工具

### 接口

| 工具 | 参数 | 程序行为与返回 |
|---|---|---|
| `move_base` | `turn_rad`（先原地转向）、`forward_m`（再沿新朝向直行，负值为后退） | 先转后直行。Fetch 是差速底盘，不能横移。执行时手臂保持当前关节目标，夹爪保持当前指令。返回：要求与实际达到的转角和位移、用掉的步数、是否被官方终止 |

- **单次指令范围**（初拟）：|`turn_rad`| ≤ π，|`forward_m`| ≤ 1.5 m。
- **速度上限**（初拟）：0.5 m/s、1.0 rad/s。按 ManiSkill 默认控制频率 20 Hz（运行时核实），约为每步 2.5 cm、0.05 rad。
  - 官方控制器上限为 1 m/s、3.14 rad/s；
  - 救回扫描曾用 0.25 m/s、0.6 rad/s，按那个速度，1 m 就要占用 200 步中的 80 步；
  - SAC 第 11 号在 50 步内移动了 1.06 m。
  - 速度上限在底盘冒烟测试后冻结。
- **到位判据**：位移 ≤ 0.02 m、转角 ≤ 0.03 rad，每条指令最多 80 步，与救回扫描一致。未到位时如实返回剩余误差。
- **步数**：底盘与手臂共用官方 Pick 的 200 步。

### 执行方式（输入规则）

- **只用里程计闭环**：里程计是"相对本次尝试开始时底盘坐标系"的 (Δx, Δy, Δyaw)，由底盘关节量 `qpos[0:3]` 的变化换算得到。
  - 换算公式与坐标系约定，在 CPU 硬门中用 URDF 和已记录的数据核对；
  - 里程计是无噪声的理想值，报告时注明。
- **不做路线预检，不做碰撞过滤**。撞了由官方累计力上限判定。
- **不能直接复用的现有代码**：
  - `src/bvi/segmented_base_control.py` 的输入是底盘在世界坐标系里的绝对位姿；其跟踪算法可以复用，但输入必须换成里程计坐标；
  - `scripts/run_real_handoff_rescue_condition.py` 用官方地面网格（`NearPickFloorRoute`）检查并拒绝路线。

  两者按 9/27 输入规则都不能进主条件。
- **观测新增**：每轮观测附上里程计。底盘移动后，末端工具的坐标系是**当前** `base_link`，工具说明要写明这一点。

### 特权目标位置

- 仍为目标碰撞形状包围盒中心，只在第一次请求中给一次，不给朝向和尺寸。
- **坐标系为"尝试开始时的 `base_link`"**。底盘移动后，由 Astra 结合里程计自行换算，程序不重新发送真值，也不代为换算。

## CPU 硬门（任一项不过，不得申请 GPU）

1. **单元测试**：原有测试全部通过。新增测试覆盖：
   - 段终点按实测状态更新（用 E1 第 8 号的场景做回归）；
   - 工具参数校验与错误信息；
   - `move_base` 先转后直行、到位判据、步数上限、官方终止处理；
   - 里程计换算正确，且相对坐标系不暴露绝对位姿；
   - 底盘移动时手臂与夹爪保持不变。
2. **坐标与动作映射**：
   - 底盘动作在动作向量中的位置与含义（前进速度、角速度）；
   - `qpos[0:3]` 的语义；
   - 用已记录的 SAC 教师轨迹核对：里程计换算出的底盘位移，与 URDF 正运动学得到的 `base_link` 相对位移一致。
3. **请求审计器更新**：允许里程计字段；拒绝绝对底盘位姿、世界坐标、导航网格及路线信息。

## 第一步：底盘冒烟测试

**目的**：确认 `move_base` 按指令到位、步数合理，并且只用了里程计。不要求抓取。

**样本与指令**（写死，不经模型）：

1. **救回扫描中实际完成过的底盘动作**：从救回扫描的起点中，选开发集的 2 个起点。每个起点取 1 个转向、1 个直行，都要求是当时实际执行完成、未被官方终止的动作，按原转角或距离下达。
   - 救回扫描的起点包括测试集交接，只能选开发集的。
2. **SAC 在抓取时刻的底盘净位移**：第 5、8、11 号交接，各拆为两次 `move_base`（先转与直行，再只转向），目标是 SAC 到抓取帧 g 时的底盘净位移。用户已确认两次调用合计最多80步；同时检查最终净位姿误差。帧g固定为第5/8/11号的7/17/24。
   - 路径和 SAC 不同，不保证无碰撞；
   - 发生力超限时，评估端列出接触物体，不自动归因于执行器。

具体起点、动作与帧号在授权提案中冻结。

**通过标准**：
- 每条指令都到位（≤ 0.02 m／0.03 rad），且在 80 步以内；
- 里程计与评估端真值位移的差 ≤ 0.01 m／0.01 rad；
- 没有使用任何被禁止的输入；
- 没有被官方终止。

**资源（待批准）**：实验室 GPU1 串行，5 个进程 × 180 秒 = **900 进程秒**，API 0。

## 第二步：按可达性给开发集分层（只用 CPU，评估端）

## v13 修订（用户 2026-09-29 决定）

依据 [v13 草案](real-handoff-eef-base-control-v13-revision-proposal.md) 和[第 11 号 CPU 归因](../diagnostics/2026-09-29-eef-base-turn-drift-cpu/README.md)，用户作出三项决定。

### 失败分类（写在修订前）

| 来源 | 现象 | 性质 |
|---|---|---|

| v12 剩余批次，第 8 号 | 两次调用的残差累积，超出净航向门；第二次调用的小角度落在容差死区内，0 步返回 | 冒烟脚本的指令拆分规则问题；r3 已修，物理复测通过 |

原有失败记录全部保留原判，不追溯修改。

### 决定 1：先停稳再动，范围扩大到每次尝试开始时

- `move_base` 的每个运动阶段（转向、直行、以及第二次调用的转向）开始前，先向官方底盘控制器发零前进、零角速度，同时保持躯干、头部、手臂的目标与夹爪指令，直到底盘停稳才开始动作。
- **每次尝试开始时、任何工具执行之前，也先停稳。** 交接时底盘可能仍在运动：第 11 号第 1 步末的实测底盘速度约 0.72 m/s。底盘在滑动时，手臂工具的目标相对机器人也在移动。
- 停稳判据只用本体量：底盘关节速度（qvel）或相邻里程计的变化，连续若干步低于阈值。传感量、阈值、连续步数在 CPU 阶段冻结。不得用接触信息或场景几何来触发停稳。
- 停稳所用步数计入该次调用的步数和官方 200 步。停不下来时如实返回未完成。

### 决定 2：转向和直行都用刹车曲线，取代"增益改为 4"

- **做法**：先以最大速度运动；按剩余量能允许的减速度提前减速，指令为 `min(v_max, √(2·a·|e|))`；最后几步用小比例增益收尾，直到进入容差。
  - 转向：ω_max = 1.0 rad/s；
  - 直行：v_max = 0.5 m/s。
  - 两个速度上限都不变。
- **为什么不用增益 4**：比例控制本身就有"越接近越慢"的长尾，增益 4 只是把尾巴缩短一半，而且这个数是从失败案例反推出来的。刹车曲线能在有限步内收敛，也与手臂躯干用的梯形速度曲线是同一思路。
- **直行也改**：直行阶段同样有比例控制的收尾长尾。本次一并改成刹车曲线，免得以后再为直行出一个新版本。
- **减速度怎样定**：只用已有记录中**无接触**的片段，拟合官方底盘控制器的速度响应后确定，不在第 11 号的失败片段上调参。
  - 无接触时，角速度跟踪误差约 0.013 rad/s，控制器跟得上速度指令。
- **CPU 检查**：理想响应，以及带一步延迟、饱和、速度扰动的稳定性检查。不以替代模型的预测作为物理通过的依据。

保留 v13 草案第 3、4 条：
- 不加横移通道，不做路线预检；接触造成的漂移如实返回；
- 评估端逐次调用记录入口与出口的 qpos、qvel、停稳步数、指令与实际速度；接触日志补上外部实体标识，只用于评估。

### 决定 3：冒烟门拆成"工具契约门"与"场景报告"；v13 是冒烟的最后一个版本

**工具契约门**（阻塞，全部满足才进入 E1-B）：

| 契约 | 判据 |
|---|---|
| 先停稳 | 每次运动前满足冻结的停稳判据，所用步数如实记录 |
| 里程计准确 | 全程与评估端真值的差 ≤ 0.01 m／0.01 rad |
| 无接触时按指令到位 | 每次调用 ≤ 80 步，到位误差 ≤ 0.02 m／0.03 rad |

| 接触时如实返回 | 返回的实际位移与里程计一致，不隐瞒残差 |

- **契约样本**：开发集起点 20、23。每个起点从冻结快照独立恢复，执行四条救回扫描动作库里的指令：左转 0.1 rad、前进 0.1 m、转向 0.35 rad、前进 0.3 m。后两条用来检验刹车曲线。
  - 所选动作须在救回扫描中于同一起点实际执行完成、未被官方终止；GPT 在提案中核对并冻结。
  - 若某条动作在该起点从未执行过，换用动作库中同类的已执行动作，并写明替换依据。

**场景报告**（不阻塞，只报告）：第 5、8、11 号的"SAC 净位移"两次调用序列。
- 每次调用 ≤ 80 步，恢复设计原文；两次合计不再单独设限，仍受官方 200 步约束。
- 报告：最终 XY 与航向误差、各阶段步数、停稳步数、评估端接触记录。
- 不阻塞的理由：
  - 这是拿 SAC 当标尺的组合场景，拆出的路线贴着家具走，本身就容易接触；
  - Astra 闭环使用工具，残差可以靠下一次调用补上；手臂工具工作在当前 `base_link` 下，只要里程计准确，底盘差几厘米不影响；
  - 接触由官方累计力判定，是 Astra 要自己应对的环境结果。

**停止规则**：
- v13 是底盘冒烟的最后一个版本。工具契约门通过就准备 E1-B 提案，场景报告的结果一并写进 E1-B 的背景说明。

- 不自动归因躯干，不自动锁定躯干。
