## 一、审查结论：最近的修复为什么没见效

依据 9/30 以来的诊断：visual r1/r2、compact-640 r1–r3、r3 离线跟进、协调接口 r1/r2、网络诊断。

1. **每次只修一个症状，底层结构没变。**
   - 执行器叠加了多层规则：末端路径加密、IK8 规划、躯干独立梯形曲线、运行时按实测躯干做 IK7 补偿、模型逆前馈、逐点放行、停稳前奏、每次移动 60 步上限。规则组合在一起会互相卡住。
   - 9/28 以来约有 15 个执行器版本，每修一个问题，下一个就暴露出来。
   - 例：r3 第 5 号两次 `move_to` 都跑满 60 步，IK 等待分别占 26 步和 52 步。离线重建查明，是固定躯干高度下 IK7 求不出解，而 IK8 可解。协调 v1/v2 把 IK 等待降到 0，但仍未在 60 步内到位。
2. **待验证假设：逐点放行可能限制末段推进。**
   - 协调 v2 的末段：参考点 47 停留 4 步，48 停留 5 步，49 停留 6 步；57 个参考点只有 60 步。
   - 这与 v1"每个点都等收敛"属于同一类问题。
3. **验证样本太窄**：几乎每个版本都只在第 5 号的 1–2 条移动上做物理验证。
4. **实验条件同时在变**：特权位置 → 纯视觉；128 → 2048 → 640 px；历史方式、方法指导 v1–v4、`look` 与 `recall_observation` 陆续加入。失败无法归因。
5. **网络删失**：
   - 9/30 以来 6 次试点被网络中断，约 64 次发送中有 8 次传输失败（约 12%）；
   - 失败集中在请求达到 MB 级之后，9/29 用 128 px 小图的 46 次请求没有断过；
   - 都发生在本机 Wi-Fi/VPN 上。有界补发能恢复部分发送，但网络根因尚未确定；迁移服务器是否降低失败率仍须验证。

**研究进度**：新样本上还没有一次严格成功（E1-B 0/4，E1-B2 已完成的 0/2，视觉试点已完成的 0/2）。严格成功只有第 5 号的两次，而第 5 号参与过多轮执行器调试。H1（带历史的重试）一次都还没跑。

## 二、冻结实验条件

执行器达标前，模型侧条件一律不改。冻结内容：
- 视觉主条件：首轮起就不给目标真值位置，只给目标语义。
- 头部、手部 640×640 RGB-D，按 compact-640 设计的近期图像窗口与显式文字历史。
- 提示 `guidance-v4-compact`；工具 schema 维持现状：`look`、`locate_point`、`recall_observation`、`check_path`、`move_to`、`move_eef_chunk`、`set_gripper`、`return_to_rest`、`move_base`、`done`、`give_up`；每条调用都带 `note`。
- `gpt-6-astra` medium；每次尝试最多 25 次工具调用；官方 200 步；H0 单次；终止后最多一次反思。
- 底盘沿用 v13（停稳、刹车曲线、限速）。

**本阶段唯一允许修改的是末端执行器内部**，且只能按第四节的流程修改。模型侧任何改动（提示、分辨率、工具、历史方式）都须另记版本并经用户批准。

## 三、基础工作

### 1. API 调用搬到实验室服务器

- **原因**：约 12% 的传输失败集中在本机 Wi-Fi/VPN 上传 MB 级请求时。
- **做法**：API 代理（broker）在实验室服务器上运行，与仿真进程同机或同网段。
  - 先核对服务器出网是否可达 API 端点：做一次不带密钥的连通性探测，预期返回 401。
  - 保留有界补发（bounded-transport-v2）与分阶段日志：TCP、TLS、发送、等待响应头、读取正文。
- **凭证安全**：服务器是共享的（GPU0 上有其他用户的进程）。
  - 密钥只放在服务器上被忽略的本地配置文件里，权限 600，绝不写进日志、仓库或聊天；
  - **建议为服务器单独使用一个设有消费上限的 API 密钥**。由用户决定并亲自放置，协作代理不经手密钥内容。
- **已完成（2026-09-30，用户操作）**：
  - 用户已在实验室服务器放置 `~/.config/bvi/openai.env`，内容为一行 `OPENAI_API_KEY=...`；目录权限 700，文件权限 600；
  - 用户在服务器上带密钥请求 `/v1/models`，返回 200：出网可达，密钥有效；
  - 协作代理只使用这个路径：每次使用前检查权限是否为 600；不打印、不记录、不复制密钥内容；不把该文件放进仓库、`runs/`、部署包或日志；不把密钥作为命令行参数传递。
- **验收**：用冻结请求格式（640 图像、真实历史长度）发送若干次传输探测，响应只存档、不执行。统计失败率，并与本机历史的约 12% 对比。探测计入 API 预算。

### 2. 生成新的开发集交接

- **原因**：开发集 20 个交接只剩第 61 号没用过；5、55、58 已被反复使用。测试集 40 个继续不动。
- **做法**：按普查冻结的同一流程（PPO 原生导航 → 首次交接快照），在普查未用过的任务计划上生成新交接，组成"开发集 2"。
  - 目标约 20 个有效交接；导航失败的计划如实记录，不计入。
  - 每个交接跑一次官方 SAC Pick，作为评估端参考（能否成功、底盘是否移动），**不给 Astra**。
  - 在评估端按可达性分层（1.14 m 上界），只用于选样。
- 快照、计划编号、源码哈希全部冻结。开发集 2 与原 60 个交接不重叠。

## 四、执行器系统对照

以 Astra（协作代理）的修订计划为基础，做以下修改。

### 1. 先补可观测性，再做 CPU 重算

- **每个物理步记录**：计划关节目标、补偿后目标、实测 qpos／qvel、参考索引与推进原因、阻塞放行的关节、限幅前后的指令、末端误差、IK 耗时。停稳、运动、IK 等待、终点收敛的步数统一计数，不重复计算。
- **用已归档状态做只读重算**，量化三件事：实时补偿相对计划目标改变了多少；哪些关节让同一参考点停留 4–6 步；动作饱和、方向来回反复与末端误差之间的关系。

### 2. 标准移动组（取代原计划的 3 个入口）

- **15–20 条标准化移动**，起点取自至少 3 个交接，其中至少 1 个来自开发集 2 或第 61 号（未参与调试）。覆盖：
  - 从待机姿态移到桌面高度的预抓位（距离 0.5–0.9 m）；
  - 移到地面高度的预抓位（需要大幅降躯干）；
  - 竖直下降或抬起 0.10–0.15 m；
  - 2–5 cm、约 0.1 rad 的小幅修正；
  - 从低位姿回休息位；
  - 实际使用中出现过的移动：r3 第 5 号 turn 5、compact r2 第 5 号 turn 6、E1-B2 第 58 号重试 turn 8。
- 目标位姿以机器人坐标系定义，在提案中冻结。
- **接触的处理**：评估端记录接触。发生意外接触的移动单独报告，不计入计时规格；不做场景碰撞过滤。

### 3. 2×2 机制对照

| 条件 | 关节目标来源 | 参考推进方式 |
|---|---|---|
| A（基线） | 实测躯干＋实时 IK7 补偿 | 逐点放行 |
| B | 直接跟踪计划的 IK8 关节参考 | 逐点放行 |
| C | 实测躯干＋实时 IK7 补偿 | 每个运动步推进一个参考 |
| D | 直接跟踪计划的 IK8 关节参考 | 每个运动步推进一个参考 |

- 控制增益、模型参数、目标、动作限幅、终止规则、到位容差、60 步上限一律相同。
- 每条移动在四个条件下，从同一入口状态独立恢复执行，运行顺序轮换。
- **预先写明的预期**：若 C/D 明显优于 A/B，就把"按时间推进参考、只在终点收敛"定为执行器的设计原则，而不只是选出一个版本。

### 4. 达标规格（用户已在实施计划中确认）

- 无意外接触的移动，全部在 60 步内到位（≤ 0.01 m／0.05 rad）。
- 没有跳解，没有违反工具契约，没有因官方累计力上限而终止。
- **标准抓取序列**（移到预抓位 → 下降 → 闭合 → 抬起 → 回休息位）合计 ≤ 100 步且官方严格 Pick 成功；公共入口准备单列并计入原 200 步。该成功属于执行器控制证据，不是 Astra 成功。
- 报告每条移动的到位步数分布与最坏误差。

### 5. 选择、确认与停止

- 满足规格的条件，按总步数、最坏位置误差、最坏朝向误差依次排序，选第一名。
- 选中后，用标准移动组各重复 2 次做确认，全部达标才冻结。
- **没有条件达标：停下报告，交用户做方向讨论，不再开下一轮修补。**
