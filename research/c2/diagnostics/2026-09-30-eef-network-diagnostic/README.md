# C2 网络诊断：10054定位到请求建连/发送路径，根因未确定

所在阶段：C2视觉试点传输排查。推进：两批21次请求的元数据与当前Python标准库路径已核对，40次不带密钥连通性探测正常。阻塞：历史日志没有TCP/TLS/上传分段记录，无法确认重置责任端。下一门：先增加分段日志，再做单独有界传输验证；不原样重跑机器人。

## 已核实

1. r1失败请求1,828,548字节，在落盘后约0.0985秒记错；r2失败请求1,665,063字节，约0.1666秒。时间来自本地文件时间戳，是近似耗时。成功请求最大1,832,772字节；两次失败均8图。因此没有“超过固定大小就失败”证据，尚不能排除大体积上传放大偶发网络风险。
2. 错误为URLError包裹ConnectionResetError errno10054，不是HTTP429/400，也不是解析异常或180秒超时。没有response-raw.json。
3. 本机实际stdlib do_open仅在h.request(...)的OSError处包裹URLError；h.getresponse()在该包裹以外。因此这两次异常定位在建连/TLS/HTTP发送路径，不能当作模型推理失败。缺少更细堆栈，无法区分握手和上传。
4. 当前urllib每次urlopen均Connection: close，每轮新建连接；没有连接池。它不是连接重置的充分原因，也不能单凭此认定代码制造重置。
5. 当前进程无proxy环境变量，urllib.getproxies()为空；这不排除VPN、透明代理、防火墙或运营商路径。DNS正常，测试实际走IPv6。
6. 不带任何密钥、不发送实验数据的GET /v1/models共40次：16次分段socket/TLS测试、24次urllib路径测试，全部返回预期401；未复现重置。这只证明当时的小请求连通性，不验证大POST、认证、推理或长期稳定性。无证据认定IPv6是根因。

## 代码审查与后续修复建议

停止批次与未知费用预留符合冻结规则，不能为了完成实验直接给所有异常加自动重试。当前日志确实不足：只保存异常类型与errno，没有分段时长、上传进度、响应头收到标记。请求的X-Client-Request-Id也不是已验证的计费幂等保证。

建议下一版先增加TCP/TLS/发送HTTP头/发送body/等响应头/读body的阶段与耗时、发送是否开始、响应request-id等白名单字段；不得记录认证头。保持实验提示、图像、控制器不变。只有能证明尚未发送HTTP请求的连接失败，才可讨论有界重连；一旦发送可能开始，仍保留未知结局并停止，不能自动重复模型调用。

连接复用可作为后续传输方案候选，但必须独立测试，不能宣称一定修复；也不应现在盲目强制IPv4、加大超时或归因OpenAI服务故障。历史两次未知费用不追溯清零。
